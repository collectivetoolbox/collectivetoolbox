Is it better to panic than to continue if a bounds check failed when it's thought to be infallible? I know non-panicking programming is popular, but it seems far better to crash the thread than to potentially return an invalid result.




Yes, it is generally better to panic than to continue when an "infallible" bounds check fails. [1]
When an assumption you believe to be 100% true turns out to be false, your program has entered an unhandled, undefined state. Continuing execution in this state poses severe risks. [2, 3]
## Why Panicking is the Correct Choice

* Prevents Data Corruption: Running code with corrupted state can write bad data to databases or files.
* Stops Security Vulnerabilities: Heartbleed and many historic exploits happened because code continued executing with invalid bounds.
* Fails Fast: Crashing immediately makes the bug obvious and provides a clean stack trace for debugging.
* Maintains Memory Safety: In languages like Rust or Go, a panic safely unwinds or aborts before memory safety is compromised. [4, 5, 6, 7, 8]

## The Problem with "Total" Non-Panicking Programming
The popular trend of returning Result or Option types (instead of throwing exceptions or panicking) is excellent for expected errors. This includes missing files, network drops, or invalid user input. [9, 10, 11, 12]
However, using it for internal logic invariants is a mistake:

* Pollutes API Signatures: Forcing a function to return an error type for an "impossible" state forces the caller to handle an error that should never happen.
* Hides Critical Invariants: It treats a fundamental developer bug the same way it treats a normal runtime occurrence like a timeout.

## The Proper Hierarchy of Handling Failures

   1. Compile-Time Proofs: Use the type system to make the error impossible (e.g., passing a NonZeroU32 instead of checking if an integer is zero).
   2. Recoverable Errors: Use Result, Option, or error codes for external, expected environmental failures.
   3. Unrecoverable Panics: Use panic!, assert!, or crashes for internal logic violations and broken invariants. [13, 14, 15, 16, 17]

If an impossible bounds check fails, your mental model of the code is wrong. Crashing is the safest way to protect your data and your users. [18, 19, 20, 21]
