### Short Answer

**No — the current [`UTF-8e-128`](file:///workspaces/ctoolbox/src/formats/utf_8e_128/codec.rs) is not optimal.** While it preserves all of UTF-8's key invariants, it leaves a large portion of the lead-byte space (`0xF4 0x90..` through `0xFE`) unused and immediately jumps to a 2-byte `0xFF` escape header for anything above `0x10_FFFF`.

Because of that jump, **5-byte encodings do not exist at all** in the current scheme: encoding length leaps directly from **4 bytes** (at `0x10_FFFF` = `1,114,111`) to **6 bytes** (at `0x11_0000` = `1,114,112`, [`SHORT_DC_REGION_START`](file:///workspaces/ctoolbox/src/storage/minimal/global_graph_layout/regions.rs#L31)).

### 1. Why Files Get Large for Small Numbers & IDs Today

There are two distinct places where small numbers expand significantly:

#### A. In `UTF-8e-128` (`u128` Codepoint Encoding)
In [`encode_utf_8e_128_buf`](file:///workspaces/ctoolbox/src/formats/utf_8e_128/codec.rs#L56-L180):
1. **The 4-byte to 6-byte cliff at `0x11_0000` (`1,114,112`):**
   - Any value `> 0x10_FFFF` emits `[0xFF, 0x80 | L, ...L continuation bytes]`, where `L = ceil(bits / 6)` encodes the **unshifted** bit length of the integer.
   - `0x11_0000` requires 21 bits, so `L = ceil(21 / 6) = 4` continuation bytes + 2 header bytes = **6 bytes** (`[0xFF, 0x84, 0x84, 0x90, 0x80, 0x80]`).
   - Consequently, **every Short Dc (`1,114,112..=2,228,223`) and every Format Dc (`2,228,224..=3,342,335`) takes 6 bytes**. (Note: an earlier design doc in [`2026-09-09-DcString.md`](file:///workspaces/ctoolbox/docs/chats/2026-09-09-DcString.md#L64) assumed Short Dcs took 5 bytes via `0xFF 0x83`, overlooking that 3 continuation bytes only hold $3 \times 6 = 18$ bits = `262,143 < 0x10_FFFF`.)
2. **`L = 1, 2, 3` in the `0xFF` header are 100% dead code:**
   - `L = 1` (3 bytes, max `63`), `L = 2` (4 bytes, max `4,095`), and `L = 3` (5 bytes, max `262,143`) can only represent values $\le 262,143$, which are unconditionally rejected by the non-overlap check `if value <= 0x10FFFF { return None; }` in [`decode_utf_8e_128_buf`](file:///workspaces/ctoolbox/src/formats/utf_8e_128/codec.rs#L260).
   - As a result, **no `u128` value ever encodes to 5 bytes**.
3. **Lead bytes `0xF4 0x90..=0xBF` and `0xF5..=0xFE` are completely unused:**
   - Ten full lead bytes (`0xF5..=0xFE`) and three-quarters of `0xF4` are rejected rather than used for 4-, 5-, 6-, and 7-byte sequences.

#### B. In Document Character Numeral Frames (`dc_number_minimal.rs`)
When an integer literal (even `0` or `1`) is encoded as a semantic Document Character number via [`u128_to_dc_number_chars`](file:///workspaces/ctoolbox/src/formats/dcdata/dc_number_minimal.rs#L114-L146), it emits a 4-token frame (`Begin number`, `Format 199`, Base64 digit Short Dc, `End number`). Because each of those 4 tokens is a Short Dc or Format Dc (6 bytes each in `UTF-8e-128`), a single small integer `0..=63` takes **$4 \times 6 = 24\text{ bytes}$** when serialized to `UTF-8e-128`.

### 2. What Properties Are Preserved (and Where They Differ from Standard UTF-8)

Looking at [`DcStr`](file:///workspaces/ctoolbox/src/formats/dcstring/dc_str.rs) and [`codec.rs`](file:///workspaces/ctoolbox/src/formats/utf_8e_128/codec.rs), `UTF-8e-128` relies on six core invariants:
1. **Strict superset of UTF-8 and WTF-8 on `0..=0x10_FFFF` (including unpaired/paired surrogates `0xD800..=0xDFFF`):**
   - All `1,112,064` Unicode scalar values encode identically to RFC 3629 UTF-8, making `From<&str> for &DcStr` ([`dc_str.rs:199`](file:///workspaces/ctoolbox/src/formats/dcstring/dc_str.rs#L199-L211)) a sound, zero-cost cast.
   - To cover the full `0..=u128::MAX` integer domain without gaps or `memcmp` ordering inversions around `0xD800..=0xDFFF`, surrogate integers (`55,296..=57,343`) are encoded as canonical 3-byte sequences (`0xED 0xA0 0x80`..=`0xED 0xBF 0xBF`, as tested in [`dcts.rs:293`](file:///workspaces/ctoolbox/src/formats/dcstring/converters/dcts.rs#L293-L296)). Unlike WTF-8, adjacent surrogate codepoints `[0xD800, 0xDC00]` are **not** coalesced into `0x10000`, because each `DcChar(u128)` is an independent integer token.
   - External tools expecting strict RFC 3629 UTF-8 will reject both surrogates and `>= 0xF4 0x90` extended sequences.
2. **ASCII/NUL transparency:** Bytes `0x00..=0x7F` never appear inside multibyte sequences.
3. **Bounded $O(1)$ self-synchronization & backward scanning:**
   - Lead byte `b0` never matches `10xxxxxx` (`(b0 & 0xC0) != 0x80`).
   - Every subsequent byte `b_i` ($i \ge 1$) always matches `10xxxxxx` (`(b_i & 0xC0) == 0x80`).
   - In valid data, a sequence contains at most **22 continuation bytes** (vs. 3 in UTF-8), powering [`DcStr::is_char_boundary`](file:///workspaces/ctoolbox/src/formats/dcstring/dc_str.rs#L135), [`DcChars::next_back`](file:///workspaces/ctoolbox/src/formats/dcstring/dc_str.rs#L389), and boundary-safe substring search (`memmem`).
   - In **malformed/untrusted data**, synchronization must bound backward scans to 22 continuation bytes and stop lossy error recovery at the first non-continuation byte (`(b & 0xC0) != 0x80`).
4. **Deterministic length from header (1–2 bytes):** For `0x00..=0xFE`, byte 0 alone determines the sequence length (`1..=7`); only `0xFF` inspects byte 1 (`total_len = 8 + ((b1 >> 2) & 0x0F)`).
5. **Byte-lexicographical order (`memcmp`) == `u128` numeric order:** [`DcStr`](file:///workspaces/ctoolbox/src/formats/dcstring/dc_str.rs#L41) derives `Ord, PartialOrd` directly on `[u8]`.
6. **Canonicality (shortest-form only):** Bijective mapping with explicit per-tier minimum value checks to reject overlong encodings.

### 3. `DcTF` (`.dctf`): A Better UTF-8-Style 128-Bit Encoding

We can preserve all six invariants above while reclaiming the unused lead-byte space (`0xF4 0x90..=0xFE`) and eliminating the 2-byte header tax in a new encoding named **`DcTF`** (`.dctf`):

1. **Use the remaining 4-byte UTF-8 space (`0xF4 0x90..=0xF7`) and classic 5-, 6-, and 7-byte unary prefixes (`0xF8..=0xFE`):**
   - **4 bytes (`0xF0..=0xF7`, `11110xxx` + 3 cont.):** 21 bits (`0x10_000..=0x1F_FFFF` = `65,536..=2,097,151`).
     - Standard Unicode uses `0x10_000..=0x10_FFFF`.
     - The remaining 4-byte space (`0x11_0000..=0x1F_FFFF`) covers **the first 983,040 Short Dcs (`0..=983,039`) in 4 bytes instead of 6 bytes**!
   - **5 bytes (`0xF8..=0xFB`, `111110xx` + 4 cont.):** 26 bits (`0x20_0000..=0x3FF_FFFF` = `2,097,152..=67,108,863`).
     - Covers the remaining Short Dcs, the **entire Format Dc region (`2,228,224..=3,342,335`)**, and Reserved Dcs up to 67M in **5 bytes instead of 6 bytes**.
   - **6 bytes (`0xFC..=0xFD`, `1111110x` + 5 cont.):** 31 bits (`0x400_0000..=0x7FFF_FFFF` = `67,108,864..=2,147,483,647`).
   - **7 bytes (`0xFE`, `11111110` + 6 cont.):** 36 bits (`0x8000_0000..=0xF_FFFF_FFFF` = `2,147,483,648..=68,719,476,735`).
     - Covers the entire `Reserved (Data)` block and the **entire `System` region (`8,589,934,592..=12,884,901,887`, 34 bits)** in **7 bytes instead of 8 bytes**.

2. **Pack both the length and the top 2 payload bits into the byte after `0xFF` (`8..=23` bytes):**
   - Once `0xF0..=0xFE` cover up to 36 bits, `0xFF` is only needed for values $\ge 2^{36}$ (37..=128 bits).
   - Instead of wasting the entire second byte `10LLLLLL` on a 6-bit length where only 16 lengths are needed, format byte 1 as `10_kkkk_bb`:
     - `kkkk` (`0..=15`): number of *additional* continuation bytes beyond 6 (`L = k + 6`, so 6 to 21 further continuation bytes, for a total sequence length of **8 to 23 bytes**).
     - `bb` (low 2 bits of byte 1): the **2 most significant bits** of the integer payload, followed by `k + 6` continuation bytes (`6(k + 6)` bits).
   - **Why unshifted bit-slicing is chosen over offset subtraction (`v - 2^36`):**
     - Payload capacity is $2 + 6(k + 6) = 38 + 6k$ bits. At $k = 15$ (23 bytes total), capacity is $2 + 6 \times 21 = \mathbf{128\text{ bits exact}}$ — eliminating the 4 wasted padding bits at `u128::MAX` and achieving the **worst-case optimal 23-byte maximum length** under the fixed `0x00..=0xFE` prefix allocation (since 21 continuation bytes after `0xFF` only carry $64^{21} = 2^{126}$ states).
     - Subtracting an offset like $2^{36}$ from extended payloads would shave 1 byte off narrow boundary intervals $[2^{38+6k},\, 2^{38+6k} + 2^{36})$, but requires 128-bit addition/overflow checks during decoding (`v + 2^36 > u128::MAX`). Keeping payloads unshifted makes encoding and decoding pure bit-shifts with zero overflow states above `u128::MAX` at $k = 15$ (while rejecting the $2^{122}$ overlong encodings below $2^{122}$).
     - Because `kkkk` is in the upper bits of byte 1 and `bb` is in the lower 2 bits, **`memcmp` ordering remains strictly identical to `u128` numeric order**.
     - Byte 1 still has prefix `10`, so `(b & 0xC0) != 0x80` boundary detection and backward iteration are unchanged.

#### Normative Tier Table & Overlong Rejection Rules

To guarantee canonicality, decoders **must** verify that every trailing byte satisfies `(b & 0xC0) == 0x80` and that the reconstructed value $v$ meets the tier's strict minimum bound `min_val`:

| Total Bytes | Byte 0 Pattern | Byte 1 Pattern | Payload Bits | Canonical Value Range (`min_val..=max_val`) |
| :---: | :---: | :---: | :---: | :--- |
| **1** | `0xxxxxxx` (`0x00..=0x7F`) | — | 7 | `0 ..= 0x7F` |
| **2** | `110xxxxx` (`0xC2..=0xDF`) | `10xxxxxx` | 11 | `0x80 ..= 0x7FF` ($2^7 ..= 2^{11}-1$) |
| **3** | `1110xxxx` (`0xE0..=0xEF`) | `10xxxxxx` | 16 | `0x800 ..= 0xFFFF` ($2^{11} ..= 2^{16}-1$, includes surrogates `0xD800..=0xDFFF`) |
| **4** | `11110xxx` (`0xF0..=0xF7`) | `10xxxxxx` | 21 | `0x1_0000 ..= 0x1F_FFFF` ($2^{16} ..= 2^{21}-1$) |
| **5** | `111110xx` (`0xF8..=0xFB`) | `10xxxxxx` | 26 | `0x20_0000 ..= 0x3FF_FFFF` ($2^{21} ..= 2^{26}-1$) |
| **6** | `1111110x` (`0xFC..=0xFD`) | `10xxxxxx` | 31 | `0x400_0000 ..= 0x7FFF_FFFF` ($2^{26} ..= 2^{31}-1$) |
| **7** | `11111110` (`0xFE`) | `10xxxxxx` | 36 | `0x8000_0000 ..= 0xF_FFFF_FFFF` ($2^{31} ..= 2^{36}-1$) |
| **8** ($k=0$) | `11111111` (`0xFF`) | `10_0000_bb` (`0x81..=0x83`) | 38 | `0x10_0000_0000 ..= 0x3F_FFFF_FFFF` ($2^{36} ..= 2^{38}-1$) |
| **$8+k$** ($1 \le k \le 15$) | `11111111` (`0xFF`) | `10_kkkk_bb` | $38 + 6k$ | $2^{32+6k} ..= 2^{38+6k}-1$ (for $k=15$: $2^{122} ..= 2^{128}-1$) |

#### Normative Malformed-Input Recovery & Versioning Rules

1. **Maximal-Subpart Error Recovery (Fixing Both [`codec.rs:365`](file:///workspaces/ctoolbox/src/formats/utf_8e_128/codec.rs#L365) and [`dc_str.rs:475, 501`](file:///workspaces/ctoolbox/src/formats/dcstring/dc_str.rs#L455-L502)):**
   - Currently, [`decode_utf_8e_128`](file:///workspaces/ctoolbox/src/formats/utf_8e_128/codec.rs#L333-L366) unconditionally returns `Some((0xFFFD, 3))` on error, and [`determine_error_len`](file:///workspaces/ctoolbox/src/formats/dcstring/dc_str.rs#L455-L502) returns `Some(expected_len)` without checking intervening bytes whenever `slice.len() >= expected_len` (so `E1 80 41` returns `Some(3)` and eats the following ASCII `'A'`).
   - **Normative rule:** At a decoding error, consume the **longest nonempty initial subsequence that can prefix a valid canonical `DcTF` sequence**; if no such prefix exists (`0x80..=0xC1`), consume 1 byte. (If the slice ends with a valid canonical prefix that is merely incomplete at EOF, return `error_len = None` so streaming decoders know to await more bytes.)
   - Because canonical `min_val` bounds constrain the first 1–2 continuation bytes, the valid canonical prefix constraints per lead byte are:
     - `0x80..=0xC1`: Cannot start any canonical sequence $\implies$ consume `1` byte.
     - `0xE0`: Byte 1 must be `0xA0..=0xBF` (otherwise `E0` alone is consumed, length `1`).
     - `0xF0`: Byte 1 must be `0x90..=0xBF`.
     - `0xF8`: Byte 1 must be `0x88..=0xBF`.
     - `0xFC`: Byte 1 must be `0x84..=0xBF`.
     - `0xFE`: Byte 1 must be `0x82..=0xBF`.
     - `0xFF`:
       - For $k = 0$: Byte 1 must be `0x81..=0x83` (`0xFF 0x80` cannot reach $2^{36}$, so `0xFF` alone is consumed, length `1`).
       - For $1 \le k \le 15$: Byte 1 is `10_kkkk_bb`. If `bb == 0`, Byte 2 must be `0x84..=0xBF` to reach $2^{32+6k}$ (if Byte 2 is `0x80..=0x83`, `[0xFF, b1]` is consumed, length `2`).
     - All subsequent bytes up to `expected_len` must be `0x80..=0xBF`.
2. **Explicit Format & Encoding Versioning (Non-Backward-Compatible Wire Change):**
   - Because legacy `DcUtf` (`UTF-8e-128` v1) sequences overlap valid `DcTF` sequences with different meanings (e.g., `FF 87 81 80 80 80 80 80 80` is `2^36` in `DcUtf` and `13,262,859,010,048` in `DcTF`), the two encodings cannot be auto-detected from raw bytes.
   - `DcTF` (`.dctf`) is therefore introduced as a distinct format while retaining `DcUtf` for legacy file load/save conversion.
