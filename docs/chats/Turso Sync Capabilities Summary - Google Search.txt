Yes, Turso Sync allows for that exact architecture (a cloud primary with multiple offline
clients), but it does not work like Google Docs or CRDTs.
While it enables the "offline-first" workflow you described, it uses a Last-Push-Wins
strategy rather than the character-by-character merging (CRDT) used by collaborative
tools like Google Docs.
1. The Architecture: Yes, it fits your description
Turso Sync is designed specifically for Local-First applications.
Cloud Server: You have a primary database hosted on Turso Cloud.
Offline Clients: Your users (clients) each have a full, local copy of the database
(embedded SQLite) on their device (phone, laptop, etc.).
Offline Work: They can read and write to this local database with zero latency,
completely offline.
Merging: When they come online, they explicitly sync changes to the cloud.
2. The Conflict Strategy: Last-Push-Wins (Not CRDT)



This is the critical difference from "Google Docs style."
Google Docs / CRDT: If User A types "Hello" and User B types "World" in the same
sentence at the same time, a CRDT merges them into "Hello World" without data
loss.
Turso Sync (Last-Push-Wins): Turso uses row-level conflict resolution.
If User A updates Row 10 and syncs...
And User B updates Row 10 (offline) and syncs 5 minutes later...
User B's update completely overwrites User A's update.
It does not automatically merge the fields or text within that row.

Why Turso Sync Fails Your Architecture



1. The ID Collision Disaster
You mentioned using incrementing integer IDs that cannot change.
The Turso Problem: If Client A (offline) creates a new node, it gets ID 105 . If Client B
(offline) creates a new node, it also gets ID 105 .
The Result: When they sync, Turso's Last-Push-Wins strategy means the client who
syncs second will completely overwrite the first client's node. ID 105 will now
belong entirely to Client B, and Client A's data is permanently lost.
The Local-First Rule: In any offline-first app, incrementing integer IDs are a strict
anti-pattern. You must use UUIDs or ULIDs (Universally Unique Lexicographically
Sortable Identifiers) so clients can generate IDs offline without collisions.
2. The Word-Processor/Text Merging Failure
You need text and relationships within a single node to merge losslessly.
The Turso Problem: As established, Turso operates at the row level. If Client A
modifies the top of a text node and Client B modifies the bottom of the same text
node while offline, Turso cannot "interleave" their changes. The database will just
pick one entire row and discard the other.

The Solution: Separate Storage by Data Type
Because your index tables are derivative and safe to discard/recompute, your entire
problem space shrinks down to just the Nodes Table.
To make this work local-first and losslessly, you need to separate your database
storage engine from your collaborative document engine.

Step 1: Use Yjs or Automerge for the Nodes Table
Instead of storing your nodes as raw text/binary blobs in a SQLite row, you should use
an established CRDT library like Yjs or Automerge.
How it handles text: They are designed exactly for rich text, word-processing
markup, and binary data. They merge concurrent offline edits character-bycharacter losslessly.
How it handles relationships: You can express your semantic triples as a Yjs Y.Map
or Y.Array inside the document. If Client A adds a relationship and Client B adds a
different relationship offline, the CRDT will merge both into the map without
overwriting.
Step 2: Fix the ID Problem with ULIDs
If changing IDs is a "no-go" because it breaks graph references, you must stop using
sequential integers before you launch an offline version.
Switch your primary keys to ULIDs.
ULIDs are 26-character strings that are monotonically sortable (like integers, they
sort by creation time) but are universally unique (like UUIDs).
Clients can safely link Node A to Node B offline, knowing the ID will never collide or
need to change upon merging.
Step 3: Use Turso Only for the Index Tables
This is where Turso (or standard local SQLite) actually shines in your stack.

1. Integer Allocation via Server-Issued Blocks (Feasible & Efficient)
Yes, your idea of preallocating ID blocks (often called a Hi-Lo ID allocation strategy or
Centralized ID Chunking) is highly feasible and completely standard for offline-first
systems where compact integer keys are non-negotiable.
In a custom UTF-8 extension where numbers encode efficiently into single or few-byte
codepoints, this is a massive performance and storage win.
How to Implement it Safely:
ghi The Server Table: Keep a tracking table in your cloud database containing
(client_id, next_available_id) .
jhi The Chunk Size: When an offline client registers or runs low, the server assigns a
chunk (e.g., a block of 10,000 IDs, like 1,000,000 to 1,010,000 ).
khi The Server Guarantee: The server updates its internal pointer to 1,010,001 and
promises never to give those IDs to anyone else.
qhi Client Autonomy: The client stores its current "high water mark" and "remaining
pool." It burns through these IDs entirely offline. If the client runs out of IDs while
completely disconnected, it simply blocks creation of new nodes until it hits Wi-Fi,
but existing nodes can still be modified and linked endlessly.

2. Merging the Proprietary Binary Format in Rust
Since your text, formatting markup, and 128-bit integer triples are intermingled in a
custom byte/UTF-8 array, Turso or standard database sync cannot merge them. You
need a Rust-native CRDT engine that can treat your custom encoding as a sequence of
operations or a hierarchical tree.
Given that you are writing in Rust, you have two premier options that can handle this:


Option A: Automerge-RS (Highly Recommended for Data + Text Structures)
automerge-rs is a mature, production-ready Rust implementation of the Automerge

CRDT. It natively understands both structured key-value maps and collaborative
sequences (text).
How to model your node: You can represent each Node as an Automerge document
containing an internal map:
"content" : An Automerge Text type or a raw byte-sequence CRDT.
"triples" : An Automerge List or Map containing your 128-bit integer pairs.

The Merging Engine: If Client A adds a triple to the metadata map and Client B edits
a line of markup text simultaneously, Automerge's merge() function combines
them perfectly into a single byte vector representing the new document state.
Option B: Yrs (The Rust port of Yjs)
yrs is an extremely high-performance Rust port of the JS ecosystem's favorite CRDT

library (Yjs).
Why choose it: It is blisteringly fast and has incredible memory efficiency, which
matches Rust's philosophy well.
How it handles text/markup: Yrs provides a YText type specifically designed for
rich text editing and formatting attributes. You can append your semantic bytes
directly into a YArray or embed them alongside the text.
