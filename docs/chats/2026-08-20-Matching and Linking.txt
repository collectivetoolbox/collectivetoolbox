There isn’t one “best” algorithm or one crate/library for all of these cases.

The usual **best approach** is a **pipeline**:

1. **Normalize**
2. **Generate a small candidate set** for each record
3. **Score candidates**
4. **Reject low-confidence matches** as “no good match”
5. **Cluster** accepted links into groups

That matters because the naive approach is \(O(N \times M)\), which is impossible at your sizes.

## What to use for each problem shape

### 1) Single-field or mostly-single-field matching
Examples:
- listen title → music track title
- noisy title → reference title

Use:
- **text normalization** first: lowercase, Unicode fold, strip punctuation, standardize “feat.”/“ft”, remove edition noise, normalize whitespace
- **candidate generation** with either:
  - character \(n\)-gram index + BM25/TF-IDF retrieval
  - MinHash/LSH for token overlap
  - ANN over character-\(n\)-gram vectors or embeddings
- **rescoring** with edit/token metrics such as Levenshtein, Damerau-Levenshtein, Jaro-Winkler, token-set/token-sort

For the scoring layer, **RapidFuzz** is a strong off-the-shelf choice in Python; it provides many string metrics, is implemented largely in C++, and recommends batched processors like `cdist` for much better throughput than per-pair calls. <citation src="1,3"></citation>

In Rust, **strsim** is a solid low-level crate for Levenshtein, Damerau-Levenshtein, Jaro/Jaro-Winkler, and Sørensen-Dice, but it is only the **string-metric layer**, not a full large-scale matching pipeline. <citation src="29,33"></citation>

### 2) Multi-field record linkage
Examples:
- title + country + year
- product title + brand + pack size + UPC + vendor metadata

Use a **record-linkage / entity-resolution** library rather than raw fuzzy-string matching.

The standard workflow is:
- **blocking / indexing**
- fieldwise comparisons
- supervised or unsupervised classification
- thresholding
- clustering

That workflow is explicitly how the Python Record Linkage Toolkit is structured, and it includes blocking, sorted-neighbourhood indexing, field comparisons, and supervised/unsupervised classifiers. It is positioned more for research and small/medium files. <citation src="24,25"></citation>

If you want a more production-oriented probabilistic linker, **Splink** is a strong default for structured multi-column matching. It uses a Fellegi–Sunter-style probabilistic model, supports unsupervised training, and is designed to scale from local DuckDB to Spark/Athena, including 100M+ record workloads. Splink also explicitly says it is **not designed for a single bag-of-words column**, so it fits your title/country/year or product-attribute cases much better than pure title-only matching. <citation src="8,9"></citation>

If you can provide labels or do active learning, **dedupe** is also a strong option for structured data; it learns matching rules from human-labeled examples and supports deduplication, record linkage, and clustering on structured data. <citation src="14,15"></citation>

## Practical recommendation by your examples

### MusicBrainz title matching: 100k → 20M track names
Best approach:
- build a **retrieval index** over the 20M reference strings
- retrieve top \(k\) candidates per query using:
  - character 3-gram BM25/TF-IDF, or
  - ANN over title vectors
- rescore top \(k\) with:
  - normalized Damerau-Levenshtein
  - token-set ratio
  - artist/album/duration if available
- accept only if:
  - top score exceeds threshold, **and**
  - top score beats second-best by a margin

For ANN, HNSW is a common choice; **hnswlib** is a lightweight ANN library with incremental indexing and cosine/L2/IP support. <citation src="19"></citation>

I would **not** do raw pairwise edit-distance against 20M titles.

### Title/country/year matching: 100k → 4M
Best approach:
- block on cheap keys first, such as:
  - normalized first token
  - year within \(\pm 1\)
  - country exact or nearby
  - title prefix/phonetic bucket
- use a **probabilistic multi-field model**
- set 3-way outputs:
  - **match**
  - **possible match / review**
  - **no match**

This is where **Splink** or **dedupe** is a much better fit than a pure fuzzy-string crate. <citation src="8,14"></citation>

### Retail products across 50 vendors; cluster “same item”
This is classic **entity resolution**:
- normalize brand, size, units, model numbers, GTIN/UPC/EAN
- block aggressively on brand/model/pack-size fragments
- compare titles with token and edit metrics
- give huge weight to exact identifiers if present
- produce pairwise match probabilities
- cluster with connected components or correlation clustering, with guardrails against transitive false positives

Again, **Splink** or **dedupe** fits this much better than plain string similarity. Dedupe even includes product-linkage examples. <citation src="8,15"></citation>

## How to detect “no good match”

This is the key design point.

Do **not** force a nearest neighbor. Instead use a **reject option**:

- require **absolute score threshold**
- require **margin from second-best**
- require **field-consistency rules**
- optionally require **calibrated probability** from a classifier
- keep a **manual-review band**

A good pattern is:

- **match** if \(p \ge 0.98\)
- **review** if \(0.80 \le p < 0.98\)
- **no match** if \(p < 0.80\)

Those numbers are placeholders; tune them on labeled validation data.

## Which algorithms fit which complexity level

### Small data
If total comparisons after blocking are in the low millions:
- edit distance
- Jaro-Winkler
- token-set/token-sort
- simple logistic regression / EM classifier

### Medium data
If you have 100k–a few million records:
- blocking or sorted neighbourhood is mandatory
- use fieldwise probabilistic linkage
- batch scoring
- maybe DuckDB/Spark backend

### Very large single-field catalogs
If candidate universe is 10M+ strings:
- first-stage retrieval/indexing is mandatory
- ANN or IR-style retrieval first
- edit distance only on top \(k\)

## My short “default stack” recommendations

### If you want the fastest path in Python
- **single text field only:** retrieval index + **RapidFuzz**
- **multi-field linkage/clustering:** **Splink**
- **multi-field with human labeling / active learning:** **dedupe** <citation src="1,8,14"></citation>

### If you want Rust
- use **strsim** for the metric layer
- pair it with:
  - your own blocking/indexing, or
  - an ANN/search library for candidate generation
- for very large text catalogs, build retrieval first and use `strsim` only for reranking <citation src="29,33,19"></citation>

## Bottom line

For your use cases, the “typical best algorithm” is **not one fuzzy metric**. It is:

**candidate generation + probabilistic scoring + thresholded rejection + clustering**

And yes, **the right algorithm absolutely changes with set size and field structure**:

- **single-column huge catalog** → retrieval/ANN + reranking
- **multi-column structured records** → record linkage / entity resolution
- **product clustering** → entity resolution + graph clustering
