### 7. Architectural Evaluation: Freezing Syntax Rules Now vs. Moving Parsing Logic into the Graph First

Your instinct at the end of your question hits on the core architectural issue: **freezing the syntax rules as globally immutable right now would be premature and counterproductive**, whereas **versioning syntax rules and moving the parsing logic into the graph** gives you permanent backwards compatibility without locking in current limitations.

Specifically:
1. **Why freezing syntax rules now is risky**:
   - Even this small audit of existing `.sems` and `.legacy_cdce` fixtures exposed three places where the current rules are either too strict or incomplete:
     1. Empty comments (`Dc 246 "Begin single-line source comment on current line"` `Dc 248 "End single-line source comment"` in `at-comment.sems`) are rejected by `[^248 255]+`.
     2. Recursive/indexed identifiers (`Dc 270 "Begin identifier"` containing `Dc 277 "Reference list element"` and a nested `Dc 270 "Begin identifier"`..`Dc 271 "End identifier"` in `invoke.sems`) and bare `.EL Types` tokens are rejected.
     3. Legacy Weave `CdceLegacy` (`"f93"`) documents use `Dc 2 "Begin separator"`..`Dc 3 "End separator"` and unframed numbers/dates that conflict with modern `Dc 6 "Begin number"`..`Dc 7 "End number"` rules—and adding a rule for `Dc 2 "Begin separator"`..`Dc 3 "End separator"` breaks `1 2 # ⚽` in `eite.sems`.
   - If syntax rules are declared frozen/immutable globally, you cannot fix `[^248 255]+` -> `[^248 255]*`, add recursive subpatterns to `Dc 270 "Begin identifier"`, or refine `.EL` routine/parameter grammar without violating the freeze.
2. **Why moving the parsing logic (and versioned syntax profiles) into the graph solves this cleanly**:
   - The graph already has the ontology for statement-level evolution: `Dc 617 "Begin graph node definition"`..`Dc 618 "End graph node definition"`, `Dc 594 "Syntax rule"`, `Dc 591 "Supersedes"`, `Dc 592 "Retracts"`, and `Dc 397 "Equivalent representations"`.
   - If a document (or format variant such as `CdceLegacy` `"f93"` vs modern `DcText` `"f88"`) binds to the graph node of its syntax rule set and parser implementation:
     - Old documents remain permanently parseable using the graph node of the syntax rules and parser they were written against.
     - Newer syntax rules can supersede (`Dc 591 "Supersedes"`) older `Dc 594 "Syntax rule"` statements in the graph without breaking existing documents or requiring ad-hoc legacy fallbacks in a single global grammar.
