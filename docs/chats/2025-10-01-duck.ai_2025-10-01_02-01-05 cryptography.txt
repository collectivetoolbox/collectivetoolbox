## High-level picture

- **Key = random bytes used by cryptographic algorithms** (symmetric keys).  
- **Public/private keys** are an asymmetric pair where operations are easy one way (encrypt/sign with public/private) and hard to reverse without the other key.  
- Typical app crypto separates *authentication/session* from *data encryption* and *transport/authenticity*.

## Concepts (very short)

- **Password** — low-entropy secret the user types. Never used directly as a crypto key.  
- **KDF (Key Derivation Function)** — stretches a password into a high-entropy key (e.g., PBKDF2, scrypt, Argon2). Output: a symmetric key.  
- **Session key** — short-lived symmetric key used to encrypt/authenticate a user’s session (e.g., TLS session keys or a server-side session token mapped to server state).  
- **KEK (Key Encryption Key)** — a key whose job is to encrypt/decrypt other keys (wrap/unwrap).  
- **DEK (Data Encryption Key)** — the key that actually encrypts/decrypts user data (files, database fields).  
- **AEAD (Authenticated Encryption with Associated Data)** — an encryption mode that provides confidentiality + integrity in one operation (e.g., AES-GCM, ChaCha20-Poly1305).  
- **AAD (Additional/Associated Authenticated Data)** — data included in AEAD integrity checks but not encrypted (e.g., record headers, user id, version).

## How they relate in a common app flow

1. User creates password → app stores salt + KDF parameters.  
   - Password + salt + KDF → a derived symmetric key (call it PW_KEY).
2. Authentication / session:
   - PW_KEY (or a hash of it) is used to authenticate the user to the server. More commonly, server verifies credentials and issues a session token or establishes a TLS session.
   - Session keys (symmetric) secure the connection or are used to sign/validate API calls while the session is active.
3. Data encryption layers:
   - DEK is generated randomly to encrypt user data with AEAD (e.g., AES-GCM). DEK is what actually encrypts files/records.
   - DEK is stored encrypted (wrapped) using a KEK. The KEK might be derived from the user’s password (PW_KEY) or from a server-side secret depending on your threat model.
     - If KEK = derived from PW_KEY: Only user (who knows password) can unwrap DEK — good for zero-knowledge/encryption-at-rest model.
     - If KEK = server-side key: Server can decrypt DEK for operations but server must be trusted.
4. AEAD + AAD:
   - When encrypting with DEK use AEAD for confidentiality + integrity.
   - Include AAD such as object IDs, version numbers, or user ID so any tampering with AAD will fail authentication when decrypting.
5. Asymmetric keys (public/private):
   - Used for authentication, key exchange, signatures, or to bootstrap secure channels.
   - Example: Server has an SSL/TLS private key; clients use server public key to verify server identity and establish a secure channel (which results in symmetric session keys).
   - You can also use asymmetric keys for encrypting a symmetric DEK to a recipient’s public key (hybrid encryption).

## Concrete minimal example (common design)

- On signup:
  1. Generate random DEK. Encrypt user data with DEK using AEAD. Store ciphertext + nonce + AAD metadata.
  2. Derive PW_KEY = KDF(password, salt). Encrypt (wrap) DEK with KEK = PW_KEY (or use an intermediate KEK and wrap multiple times). Store wrapped_DEK.
  3. Store salt, KDF params, wrapped_DEK, and ciphertext.
- On login:
  1. Derive PW_KEY from password + salt.
  2. Unwrap DEK using PW_KEY.
  3. Use DEK to decrypt data via AEAD (verifies integrity using AAD).
  4. Issue session token / establish TLS session to protect further communication.
- Server identity:
  - Server keeps a private key; client verifies server via its public key (TLS). This ensures the client is talking to the real server.

## Quick mapping of terms to roles

- Key (generic) — random bytes used by crypto algorithms.  
- Password — user secret; low entropy; input to KDF.  
- KDF — converts password → symmetric key (used as KEK or auth secret).  
- KEK — encrypts/wraps other keys (e.g., DEK).  
- DEK — encrypts actual data (use AEAD).  
- Session key — short-lived symmetric key for protecting transport or session state.  
- AEAD — encryption mode providing confidentiality + integrity.  
- AAD — extra authenticated metadata not encrypted but integrity-protected.

## Short security tips

- Never use raw passwords as keys — always use a strong KDF (Argon2/scrypt) with per-user salt and high parameters appropriate for your threat model.  
- Use AEAD (AES-GCM or ChaCha20-Poly1305) for data encryption. Include a version and object ID in AAD.  
- Prefer random DEKs per user/object and wrap them with a KEK. For client-side-only access, derive KEK from the password; for server-accessible data, use a server KEK stored in a hardware root or secret manager.  
- Use TLS (server private key + client verification) for transport; do not roll your own protocol.

pepper
- What it is: A secret value (single global secret or per-server secret) added to passwords before hashing, kept off the user database.
- Purpose: Makes it harder for an attacker who steals the password database to crack passwords, because they also need the pepper.
- How to use: Combine password + salt + pepper, then run a slow KDF (bcrypt/Argon2/scrypt). Store salt and hash in DB; store pepper separately (e.g., in secure server config or HSM). If pepper is compromised, you still have salts + slow hash but attackers have easier offline cracking.

post-quantum (PQ crypto)
- What it is: Cryptographic algorithms believed resistant to attacks by large quantum computers (unlike RSA/ECDSA which quantum algorithms can break).
- Relevance: Use for long-term confidentiality or for systems that must remain secure if large quantum computers appear.
- Practical advice: For now, hybrid approaches are common — combine classical algorithms (e.g., ECDH) with a post-quantum KEM or signature so an attacker must break both. Follow NIST standards and vendor guidance for migration.

nonce
- What it is: A number used once — usually a unique per-encryption value that prevents repetition and replays.
- Not the same as salt exactly:
  - Salt: used in hashing (e.g., password hashing) to make identical passwords produce different hashes and slow rainbow table attacks. Salt is usually stored with the hash.
  - Nonce: used in encryption operations (especially AEAD). It must be unique for a given key (sometimes unpredictable is required, sometimes just unique).
- Storage: For AEAD, you typically store ciphertext + nonce + AAD metadata so the receiver can decrypt and verify.

perfect forward secrecy (PFS)
- What it is: Property that compromise of long-term keys (like a server’s private key) does not allow an attacker to decrypt past session traffic.
- How it’s achieved: Use ephemeral key exchange (e.g., ephemeral Diffie–Hellman, ECDHE) — each session uses a fresh ephemeral key, so even if the server’s signing key is later stolen, past session keys cannot be reconstructed.
- When to use: Always for TLS and session protocols that need strong privacy for past sessions.

How these relate to your earlier mental model
- Passwords → session: Users authenticate with a password. Server verifies password (using salt + slow KDF + optional pepper). Successful auth can create a session token or derive a session key (often using asymmetric TLS to protect the login).
- Passwords → data key: If you encrypt user data client-side, you typically derive a data-encryption key (DEK) from the password (KDF with salt) or wrap a random DEK with a key-encryption key (KEK) derived from the password. This allows rekeying and avoids re-encrypting large data when user changes password.
  - Typical flow: generate random DEK; encrypt data with DEK (AEAD); wrap DEK with KEK = KDF(password, salt); store wrapped DEK + salt + ciphertext.
- Server private/public keys: Used for authenticating the server to clients and for establishing secure channels (TLS). They’re not generally used to encrypt user data directly unless doing hybrid schemes. Use ephemeral ECDHE in TLS for PFS.

Quick mapping of terms to roles
- Random key: symmetric DEK (encrypt data), KEK (wrap DEK), session keys (symmetric for a connection).
- Asymmetric keys: server private/public (sign or decrypt/establish TLS); client public/private if using client certs or device keys.
- AEAD (Authenticated Encryption with Associated Data): Preferred cipher mode for encrypting data. It gives confidentiality + integrity. You supply:
  - Key (DEK)
  - Nonce (unique per encryption under that key)
  - AAD (Additional Authenticated Data), which is not encrypted but is integrity-protected (e.g., metadata like record IDs, version numbers).
  - Ciphertext (stored/sent).
- AAD vs metadata: Use AAD for any header/metadata you want integrity-protected but not encrypted. Store it alongside ciphertext.

1. Account creation:
   - User chooses password.
   - Server generates salt; compute KEK = KDF(password, salt, [pepper]).

- AAD: include fields you need integrity for (IDs, version, user ID) so tampering is detected.

- Transport: TLS with ECDHE (or modern TLS with PQ hybrids when available) for PFS.
- Key management: Use DEKs for data, KEKs for wrapping, and rotate/escrow carefully.
- Threat model: choose server-side vs client-side encryption based on whether the provider should be able to read plaintext.

## Short answer
A cryptographic ratchet is a key-evolution technique used in modern end‑to‑end messaging (e.g., Signal, Matrix Olm/Megolm) that repeatedly derives fresh encryption keys so each message (or short sequence of messages) uses a new key. It provides forward secrecy, limits the damage if keys are exposed, and supports asynchronous, multi‑device communication in ways TLS and a single static public‑key pair do not.

## Why not just TLS or “public keys” between users
- **TLS is point-to-point, transport-layer:** TLS secures a connection between two endpoints at that moment. It protects in‑transit data against network attackers but assumes the endpoints’ long‑term keys remain safe and that the connection is live. It doesn’t give strong message-level forward secrecy or easy asynchronous messaging across devices.
- **Static public keys alone lack per-message secrecy and asynchronous UX:** If you simply encrypt messages with a recipient’s static public key, an attacker who later obtains the recipient’s private key can decrypt all past ciphertexts. That defeats forward secrecy.
- **Multi-device & offline delivery needs extra machinery:** Messaging systems must handle users having multiple devices, devices that are offline, retries, and out‑of‑order delivery. Ratchets + prekeys let a sender establish a shared secret without the recipient being online and then rotate keys per message.

## What a ratchet actually does (conceptually)
- Mixes two ideas:
  - A symmetric KDF (hash) ratchet: advance a chain to derive one-time message keys from a chain key. Each advance produces a new message key and updates the chain so past keys can’t be recomputed from future ones.
  - A Diffie‑Hellman (DH) ratchet: occasionally perform a DH exchange (new ephemeral key pair) between parties to inject new entropy into the root secret, so compromise recovery and stronger forward secrecy are possible.
- Combined (Double Ratchet): every message or message block gets its own key; DH exchanges periodically re-seed the chains so future keys are independent of past compromises.

## Forward secrecy and “break‑in recovery”
- **Forward secrecy:** If an attacker later gets your device keys, they still cannot decrypt previously derived message keys (because keys were erased and derived one‑way).
- **Break‑in recovery (post‑compromise security):** After compromise, once the parties perform a DH ratchet (exchange new ephemeral keys), future keys become secure again — the attacker loses access automatically.

## Groups and scalability (Olm vs Megolm / Signal vs Matrix)
- Two‑party Signal-style double ratchet gives the strongest per‑message guarantees.
- Group chat is harder: naive pairwise ratcheting scales poorly. Matrix uses:
  - **Olm** for device‑to‑device sessions (1:1) and bootstrapping.
  - **Megolm** (a group ratchet): a sender maintains a symmetric group key that is ratcheted per message and periodically rotated and re‑shared to participants. This is more scalable but trades a small window of extra exposure if a group key is leaked (you can configure rotation frequency).
- In short: groups usually use a hybrid: secure pairwise channels to distribute group keys, and a group ratchet for message throughput.

## Do you need ratchets for collaborative editing (CRDTs)?
- Requirements differ by threat model:
  - If you only need confidentiality in transit on a trusted server, TLS might be enough.
  - If you want true end‑to‑end confidentiality so the server can’t read edits, and you want resistance to future key compromise and asynchronous multi‑device editing, then ratchets (or at least per‑message/per‑operation keys and forward secrecy) are advisable.
- Practical options:
  - Use pairwise ratchets between each device that participates and send CRDT operations encrypted per-device or per-room (Matrix-style).
  - Or use an E2EE group protocol (Megolm-like) where one device signs/ratchets the shared group key and broadcasts encrypted ops. Rotate/rotate-on-join to limit exposure.
  - If multi-author edits require collaborative merging and many devices, balance performance vs. security: frequent group key rotation reduces risk but costs extra rekey messages.

## Practical recommendations for your app
1. Use a battle‑tested library/protocol (Signal protocol / libsignal / Olm/vodozemac) instead of rolling your own.
2. If you need group editing with many participants, adopt a hybrid:
   - Per‑device pairwise sessions (ratchets) to distribute short‑lived group keys.
   - Use a symmetric group ratchet for encrypting the bulk of CRDT ops; rotate it periodically or on membership change.
3. Store minimal long‑term keys on device; design key backup/transfer carefully for multi‑device use (secure key backup or cross‑signing).
4. Erase ephemeral keys and message keys after use; use authenticated encryption (AEAD), signatures, and replay protection.
5. Define your threat model and configure rotation frequency: more rotation = better post‑compromise guarantees but higher bandwidth/complexity.
6. Test with existing E2EE clients and read implementations (Signal Double Ratchet spec, Matrix Olm/Megolm docs).

Short answer: double ratchets and TLS solve different problems. Browsers mostly use TLS because it’s the right tradeoff for authenticated, ephemeral-secure transport between two endpoints and for web ecosystem needs (performance, server authentication, proxies, CDNs). Double ratchets add properties (per-message keys, asynchronous messaging, strong forward and post-compromise secrecy) that are essential for instant-messaging and multi-device end-to-end encryption, but unnecessary or impractical as a direct replacement for TLS in the browser/web context.

Key differences (concise):

- What TLS gives you
  - Transport-level confidentiality/integrity for a TLS connection (session keys derived during handshake).
  - Server authentication via certificates and the CA ecosystem — browsers get a verified identity for the server.
  - Connection-level forward secrecy if using ephemeral key exchange (e.g., ECDHE): compromise of long-term keys doesn't reveal past session keys for that connection.
  - Designed for synchronous TLS sessions between two live endpoints, with session resumption, lots of middlebox support, and high throughput for bulk data.

- What a double ratchet gives you
  - Per-message keys derived from continuously advancing symmetric ratchets and Diffie–Hellman ratchets: each message is encrypted under a fresh key.
  - Asynchronous operation: parties can send and receive while one or both are offline. New keys are derived when messages or DH exchanges occur, so no live handshake is required.
  - Stronger forward secrecy and *post-compromise secrecy* (PCS): if an attacker compromises a device, future messages can become secure again after a DH ratchet step.
  - Built for end-to-end encrypted messaging among users/devices rather than for protecting a single transport channel.

Why browsers don’t just use double ratchets instead of TLS
- Authentication model: TLS gives a standard, widely trusted server authentication via X.509 + CA roots. Double-ratchet protocols typically rely on a different model (pre-shared keys, web-of-trust, identity keys signed by keys, or a key-distribution server). Replacing the CA ecosystem in browsers is a huge compatibility, UX, and governance change.
- Session semantics and performance: TLS handles large streaming data efficiently with negotiated cipher suites, hardware acceleration, and optimized handshakes. Double ratchets are message-oriented and add per-message key derivation overhead; they’re not optimized for web streaming or big downloads.
- Connection lifetime and middleboxes: websites rely on middlebox behaviors (CDNs, load balancers) and TLS termination models. End-to-end double ratchets would break those models or require re-architecting the web.
- Usability and deployment: TLS is transparent to users, standardized in many specs (HTTP/2, HTTP/3). Double ratchets require key discovery, identity verification UX, and storage of long-term keys per user/device — a huge change for the web.

About authentication / “vouching” in double-ratchet systems
- There is no built-in CA-like global vouching in the classic double ratchet (e.g., Signal, OMEMO/Matrix). Instead, systems use one or more of:
  - Long-term identity keys (public key per user) that are distributed out-of-band, or via a server, and verified by users (safety numbers / fingerprint comparison).
  - Key servers or identity registries that publish user identity keys; the server may sign or attest keys but if the server is malicious it can lie unless clients have independent verification.
  - Trust on first use (TOFU): accept the key first time and warn or show changes later.
  - Key transparency / append-only logs to detect key-replacement attacks (emerging approach).
- Some deployments combine server-assisted key distribution with user-visible verification (e.g., Signal’s safety numbers, Matrix’s cross-signing), which gives similar assurances to TLS certificates when properly verified — but it’s a different UX and trust model.

Do ratchets relate to forward secrecy?
- Yes. Ratchets provide forward secrecy (past messages stay safe if current keys are compromised) and go further: post-compromise secrecy (after compromise, once parties perform DH exchanges or receive new messages, future messages become secure again). TLS with ephemeral handshakes gives forward secrecy for that session but not message-level PCS across asynchronous reconnections or stored messages.

Do you need ratchets to let multiple users edit a document (CRDTs)?
- Not strictly — you need confidentiality, integrity, and authentication for CRDT messages. Options:
  - Use TLS between each client and a trusted server and have the server mediate edits (server-side storage). That’s simplest but not end-to-end.
  - Use per-peer TLS-like channels (mutual TLS) or a secure transport, but that requires online peers and key management.
  - For end-to-end encrypted collaborative editing (client-side-encrypted CRDTs), you want an asynchronous end-to-end scheme: publish encrypted operations to a server, let recipients fetch and decrypt them later. Double-ratchet-like or group-E2E schemes (e.g., MLS, pairwise ratchets with sender keys, or OMEMO-style multi-device schemes) are designed for this.
  - Practical approaches for multi-party CRDTs:
    - Use a group key per document and rotate it (but rotation and adding/removing members securely is hard).
    - Use the Sender Key pattern (Signal/OMEMO): each device has an identity key; senders encrypt a symmetric “sender key” to each recipient/device using pairwise ratchets or X3DH, then use the symmetric key for fast per-message encryption. This scales better for groups and offline recipients.
    - Consider MLS (Messaging Layer Security) for efficient, forward-secret, post-compromise-resistant group messaging with scalable membership changes — still maturing but designed for group chat / group state like collaborative docs.
- For CRDTs specifically: you need ordering/causality handling, integrity of operations (sign ops), and confidentiality for stored operations. Using an encrypted operation log (each op signed by originator, encrypted to recipients) with key management via sender-keys or MLS is a practical path.

Practical recommendations for your app (minimal, actionable)
1. Decide trust model: server-trusted vs. end-to-end. If you want true E2E, accept extra complexity for key discovery/verification.
2. For start, use an established protocol / library:
   - For pairwise messaging: use X3DH + Double Ratchet (Signal’s primitives) or libsignal-protocol.
   - For multi-device groups: consider OMEMO (Matrix) or the Signal Sender Key approach.
   - For scalable group membership with strong security properties: evaluate MLS.
3. For CRDT syncing:
   - Encrypt each CRDT operation or snapshot before uploading to server.
   - Use authenticated ops (sign operations with device identity keys).
   - Use a sender-key or group-key distribution scheme so devices can decrypt offline.
4. Key verification:
   - Implement device identity fingerprints and a UX to verify them (or cross-signing like Matrix).
   - Consider key transparency or publish signed key records on a server to detect targeted key replacement.
5. Don’t invent crypto: reuse libraries and protocols that are well-reviewed (libsignal, MLS implementations, libsodium for primitives).
6. Backup and device addition/removal: design key backup and secure device-join flows (encrypted backups, cross-signing, or invitation flows).
